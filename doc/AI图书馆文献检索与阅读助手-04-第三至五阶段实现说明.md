## 二、第三阶段：文献解析与阅读闭环

### 2.1 关键实现

- **文献分块索引**：`LiteratureIndexService#rebuild` 将以题名、作者、来源、关键词、摘要、AI 摘要组装出的语料按
  `chunkSize/chunkOverlap` 切片写入 `literature_chunk`，并更新 `literature.parse_status`（`INDEXED` / `FAILED`）。
- **分块读取**：`LiteratureIndexService#listChunks` 先做可读权限校验（`requireReadableLiterature`）再返回分块，
  在线阅读页据此渲染真实正文，未建立索引时返回空数组并引导管理员重建。
- **阅读闭环**：收藏（`literature_favorite`）、阅读历史（`reading_history`：页码、进度、阅读时长）、
  阅读笔记（`reading_note`：手动/aiGenerated）三条数据链路相互独立，均带 `deleted` 逻辑删除。

### 2.2 主要接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/literatures/{id}/view` | 文献详情聚合（文献 + 是否收藏 + 阅读进度 + 最近笔记） |
| GET | `/api/v1/literatures/{id}/chunks` | 正文分块列表（在线阅读使用） |
| POST | `/api/v1/ai/literature/{id}/index` | 重建文献分块索引 |
| POST/PUT | `/api/v1/literatures/{id}/read` | 阅读量自增 |
| GET/PUT | `/api/v1/reading-history/{literatureId}` | 阅读进度查询与保存 |
| POST/DELETE | `/api/v1/favorites/{literatureId}` | 收藏与取消收藏 |
| GET/POST/PUT/DELETE | `/api/v1/notes`、`/api/v1/notes/{id}` | 阅读笔记增删改查 |

## 三、第四阶段：LLM 与 RAG 能力

### 3.1 结构化输出与兜底

`StructuredAiService` 统一处理大模型结构化输出：首次输出按 JSON 解析并执行字段级校验（`Consumer<T> validator`），
校验失败自动发起一次“修复重试”，仍失败则调用业务兜底（`Supplier<T> fallbackSupplier`）并记录 `fallbackUsed`。
所有调用都会在 `ai_task_record` 落库（任务类型、业务类型、请求/响应快照、耗时、状态），
这为第五阶段的 AI 调用日志与健康度统计提供了数据基础。

### 3.2 能力清单

- **文献 AI 摘要**：`literature_summary_v1` 结构（背景/问题/方法/结论/创新点/关键词/适合读者），
  写入 `literature.ai_summary` 与 `summary_status`；模型不可用时基于题录生成保守兜底摘要。
- **自然语言检索**：先由模型解析意图（关键词、语种、年份区间、排序），再执行语义检索；
  解析失败退化为按分隔符切词，检索本身不中断。
- **基于原文的问答**：先检索该文献分块作为引用片段，再基于片段回答，回答与引用片段（含 chunkIndex）一并入库
  `literature_qa_record`，实现答案可追溯。
- **多文献对比**：按研究主题、方法、结论、差异、局限与后续方向输出对比分析。
- **检索行为日志**：`literature_search_log` 记录查询原文、解析关键词、检索类型、命中数量与引用数量，
  支撑第五阶段的热门关键词统计。

## 四、第五阶段：后台管理与数据统计

### 4.1 统计看板

`GET /api/v1/admin/statistics/dashboard?days&limit` 一次返回：

- `overview`：用户/文献/文件/收藏/阅读/笔记/问答/知识库/AI 任务总量与 AI 成功率、平均耗时；
- `trends`：窗口内按天的新增用户、新增文献、阅读事件、问答、AI 任务；
- `literatureStatusStats`、`literatureCategoryStats`、`userRoleStats`：文献状态、分类、角色维度分布；
- `hotLiteratures`：热门文献（阅读量、下载量、收藏数、笔记数）；
- `activeUsers`：用户活跃度排行（上传×5 + 阅读×2 + 收藏×2 + 笔记×3 + 问答×4 的活跃分）；
- `aiTaskHealth`：按任务类型的成功率、失败/超时数与平均耗时。

### 4.2 热门关键词

`GET /api/v1/admin/statistics/keywords?days&limit` 汇总三段热度并给出 `total`：

1. **文献标签热度**：全部文献 `keywords` 字段的词频；
2. **检索热度**：窗口内 `literature_search_log` 中 AI 解析关键词的词频；
3. **问答热度**：窗口内 `literature_qa_record.question` 命中词表中每个关键词的次数。

词表由 1、2 两段的规范化关键词构成（小写、去重、长度 2–32），因此问答热度是“用户提问对内容关注点的命中次数”，
可直接用于指导知识库补充与文献推荐。

### 4.3 AI 调用日志

- `GET /api/v1/admin/ai-tasks?page&size&taskType&status&keyword`：分页检索 AI 任务，支持按任务类型、状态、
  关键词（匹配任务类型、业务类型、请求/响应快照、错误信息）；请求与响应快照返回截断预览，避免管理端一次拉取大文本。
- `GET /api/v1/admin/ai-tasks/summary?days`：全局成功/失败/超时/进行中数量、成功率、平均耗时，
  以及按任务类型的健康度明细。

### 4.4 运营分析报告

`POST /api/v1/admin/statistics/report`（body：`{"days": 14}`）：

- 以统计看板与热门关键词为唯一事实来源，拼装指标文本交给大模型生成结构化报告
  （`summary` + `highlights` + `risks` + `suggestions` + `sections`）；
- 校验失败自动修复重试，模型不可用则返回基于同一份指标的本地兜底报告，响应中的 `fallbackUsed`
  标识本次是“AI 生成”还是“本地兜底”，保证管理端功能永远可用。

### 6.3 实测中发现并修复的问题

1. `GET /admin/ai-tasks/summary` 首次调用返回 500：`days` 为 null 时 `startTime(days)` 仍被求值导致
   `Integer` 拆箱 NPE，已改为先判空再计算时间下界。
2. 全局 `JacksonConfig` 将 `Long` 序列化为字符串（保护雪花 ID 精度），导致统计类数值在前端变成字符串；
   新增 DTO 的计数、字符数、耗时字段已统一改用 `Integer`，保证与前端 `number` 类型一致。

### 6.4 AI 能力状态与重试加固

**配置核对结论**：ScholarMind 与 CampusRepair 两个项目的 AI 配置完全一致（同 `base-url`、同 `api-key`、
同 `model-name: doubao-seed-2-0-lite-260428`），CampusRepair 仅多出 `app.ai.ark.token.*` 的 token 预算与降级配置。
因此不存在需要从 CampusRepair 迁移的密钥，ScholarMind 自身的配置就是可用的。

**实测结论（AI 已正常工作）**：

| 验证项 | 结果 |
| --- | --- |
| 直接调用 Ark `POST /api/v3/chat/completions` | HTTP 200，返回正常补全 |
| LangChain4j 进程内普通对话 | 成功 |
| LangChain4j 进程内 JSON 模式（`responseFormat=JSON`） | 成功 |
| `POST /admin/statistics/report` | `fallbackUsed=false`，真实 AI 生成运营报告 |
| `POST /ai/literature/{id}/summary` | `status=SUCCESS`，写入结构化摘要 |
| `POST /ai/literature/{id}/question` | 返回带 `chunk-0` 引用片段的答案 |

**此前一次失败的定位**：报错为 `UnresolvedModelServerException`。查阅 langchain4j-core 的
`ExceptionMapper$DefaultExceptionMapper` 可知，该异常由 `java.nio.channels.UnresolvedAddressException`
映射而来，属于**连接/地址解析层面的临时故障**，并非模型名或密钥错误；配置类错误（404 且响应体说明模型不存在）
会被映射为 `ModelNotFoundException`。据此判断该次失败是一次偶发的地址解析失败。

**据此完成的加固（`AiConfig`）**：

1. 模型调用增加有界重试：最多 3 次尝试，退避 800ms / 1600ms；仅重试可重试异常
   （`UnresolvedModelServerException`、`RetriableException`、超时、HTTP 429/5xx），
   配置类错误立即抛出，避免无效等待与重复计费；
2. 显式设置 `maxRetries(0)` 关闭 SDK 内置重试。实测发现两层重试会相乘——一次逻辑调用最多产生
   9 次 HTTP 请求（SDK 默认重试 2 次 × 业务层 3 次），现在重试策略统一由业务层控制，行为可预测、日志可查；
3. 新增单元测试 `AiClientRetryTest`（4 个用例）：5xx 抖动后重试成功、持续 5xx 重试 3 次后放弃、
   模型配置错误不重试、地址解析失败按退避重试。

**兜底与可观测性依旧保留**：AI 完全不可用时摘要、问答、运营报告仍会落到本地兜底实现，
失败记录写入 `ai_task_record`，可在“AI 调用日志”页排查（其中 `FAILED` 记录包含本次联调产生的历史失败）。

## 八、混合检索与 RRF 融合（第六阶段核心增强）

### 8.1 为什么不能只用向量召回

稠密向量召回擅长语义相近，但对**专有名词、术语缩写、型号、人名**等精确匹配不敏感（这些词在向量空间里往往彼此接近，
无法区分）；同时向量库不可用时整条检索链路会直接失效。稀疏检索（BM25）恰好相反：精确匹配强、可解释、无外部依赖，
但对同义改写无能为力。因此本项目采用**两路召回 + RRF 融合**，任一路失手时另一路仍能主导排序。

### 8.2 实现结构

| 组件 | 位置 | 职责 |
| --- | --- | --- |
| 稀疏召回 | `module/literature/service/retrieval/SparseRetriever` | BM25 打分（k1=1.2、b=0.75），中文采用「英文/数字词 + 汉字二元组」轻量切分，无需分词依赖 |
| 稠密召回 | `module/rag/service/MilvusLiteratureVectorService` | 文献分块向量库，独立 collection（`${collection-name}_literature`），余弦相似度检索 |
| 融合排序 | `module/literature/service/retrieval/RrfFusion` | RRF：`score(d) = Σ 1/(k + rank_i(d))`，k 默认 60 |
| 向量维护 | `module/admin/service/AdminLiteratureVectorService` | 管理端批量把已发布文献分块写入 Milvus，并回写 `vector_store_status` |
| 检索编排 | `module/literature/service/LiteratureAiService` | 语料过滤（权限 + 分类）→ 两路召回 → RRF → 可选外部重排 |

参数集中在 `app.ai.retrieval`（`RetrievalProperties`）：`enabled`、`rrf-k`、`sparse-top-k`、`dense-top-k`、
`bm25-k1`、`bm25-b`、`rerank-enabled`、`candidate-floor`。关闭 `enabled` 或 Milvus 不可用时自动退化为纯稀疏检索。

### 8.3 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/v1/search/hybrid` | 混合检索（`/search/semantic` 行为一致，命名更贴合实现） |
| POST | `/api/v1/search/retrieval-compare` | 消融对比：同时返回稀疏、稠密、RRF 融合三路排序 |
| POST | `/api/v1/admin/rag/literature-vectors/rebuild` | 把已发布文献的正文分块写入 Milvus（混合检索前置步骤） |

检索结果中的 `LiteratureReferenceChunkResponse` 新增 `sparseRank`、`denseRank`、`rrfScore`、`retriever`
四个字段，前端据此展示「稀疏#x / 向量#y / RRF 得分」，让融合过程可解释、可追溯。

### 8.4 实测数据（演示库 10 篇文献、28 个分块）

查询「RRF 融合排序 混合检索」，limit=4：

| 排名 | 稀疏名次 | 稠密名次 | RRF 得分 | 命中分块 |
| --- | --- | --- | --- | --- |
| 1 | #1 | #3 | 0.03227 | 高校数字图书馆混合推荐研究（摘要分块） |
| 2 | #2 | #5 | 0.03151 | 同上（方法分块） |
| 3 | #3 | #4 | 0.03150 | 自然语言检索意图解析（摘要分块） |
| 4 | **#7** | **#1** | 0.03132 | Hybrid Retrieval with Reciprocal Rank Fusion |

第 4 条正是融合价值的直观证据：该英文文献在 BM25 中仅排第 7（中文查询词覆盖不足），
在向量召回中排第 1，RRF 将其拉入最终前列；反向情形同样存在——查询
「如何避免纯向量召回在专有名词上的失手」时，BM25 完全未命中的分块（`sparseRank` 为空）凭借向量召回保留在结果中。

### 8.5 维度核对与自愈

实测 `doubao-embedding-text-240715` 的输出维度为 **2560**，而项目原配置为 1560，
导致 Milvus 报 `Incorrect dimension for field 'vector': dimension: 2560 is not equal to field's dimension: 1560`
（与 CampusRepair 项目对照发现其配置即为 2560）。已在 `application.yaml` 更正为 2560，
并在写入路径加入**维度自愈**：插入因维度不匹配失败时自动删除旧 collection、按当前维度重建后重试一次，
更换 embedding 模型时无需手工清理 Milvus。

## 九、论文全文解析与解析兜底

### 9.1 为什么需要

此前索引语料是用「题录 + 摘要」拼接的，并非论文正文，导致在线阅读页只能展示元数据、RAG 问答缺乏正文依据。
本阶段接入真实文档解析：文献绑定原文文件后，索引优先使用**从文件中抽取的正文**。

### 9.2 实现

| 组件 | 位置 | 职责 |
| --- | --- | --- |
| 文本抽取器 | `module/literature/service/parse/LiteratureTextExtractor` | 按内容类型/扩展名分派：PDF→PDFBox、docx→Apache POI、文本→UTF-8 解码（去 BOM、异常回落 ISO-8859-1）；统一换行、压缩多余空行 |
| 索引接入 | `module/literature/service/LiteratureIndexService#rebuild` | 通过 `S3Client` 从 RustFS 取回对象字节 → 抽取正文；正文长度 ≥ 200 字符则作为索引语料，否则回退题录摘要并写入 `parse_error` |
| 上传白名单 | `application.yaml → app.file.allowed-content-types` | 增加 docx（原仅 pdf/txt/图片/音频） |

解析链路与事务边界：远程读取与解析都被 try/catch 包裹，**解析失败不会导致索引重建整体失败**，
而是走题录兜底并记录原因（`literature.parse_error`），保证阅读与检索功能始终可用。

### 9.3 兜底与状态语义

| 情况 | 索引语料 | parse_error | parse_status | vector_store_status |
| --- | --- | --- | --- | --- |
| 抽取到足量正文 | 文件正文 | null | INDEXED | MILVUS / DB_ONLY |
| 文件类型不支持 / 解析为空 / S3 读取失败 | 题录 + 摘要 | 记录原因（≤500 字符） | INDEXED | MILVUS / DB_ONLY |
| 文献未绑定文件 | 题录 + 摘要 | 记录原因 | INDEXED | MILVUS / DB_ONLY |
| 切分后写入失败 | — | 异常信息 | FAILED | — |

### 9.4 运行时端到端验证

使用 `scripts/make-sample-pdf.ps1` 生成含专有名词（`RECIPROCAL RANK FUSION`）的最小 PDF，
再由 `scripts/verify-pdf-parsing.ps1` 走真实接口链路验证（教师上传 → 建立公开文献并绑定 →
管理员审核通过 → 重建索引 → 读取分块正文）：

| 观察点 | 实测结果 |
| --- | --- |
| 上传 | `contentType=application/pdf`，1135 字节 |
| 文献状态 | 公开文献创建后 `PENDING_REVIEW`，审核后 `PUBLISHED` |
| 索引重建 | `chunkCount=1`、`parseStatus=INDEXED` |
| 解析分支日志 | `literature text extracted ... type=PDF, textChars=424, supported=true`；`source=FILE_TEXT, fallbackReason=null` |
| 分块正文 | 含 PDF 中的关键词 `RECIPROCAL RANK FUSION`；文献摘要刻意使用不同措辞，因此该关键词只能来自 PDF 解析结果 |
| `parse_error` | `null`（未走题录兜底） |

反向分支（无绑定文件 / 解析为空）在集成测试中被覆盖，日志表现为
`source=METADATA_FALLBACK` 且 `parse_error` 记录具体原因。

### 10.4 测试发现并修复的缺陷

集成测试首次运行时暴露了两个真实缺陷，均已修复（属于「测试驱动发现的问题」，可作为论文测试章节的实证材料）：

1. **文献状态机形同虚设**：`submit` 只校验「必须为公开文献」、`approve` 只校验公开性，
   都没有校验当前状态，导致「已发布文献可再次提交回待审核」「草稿可直接被审核通过」。
   已改为：`submit` 仅允许 `DRAFT`/`REJECTED` 发起；`approve` 仅允许 `PENDING_REVIEW`；
   `reject` 原本已校验 `PENDING_REVIEW`。修复后与状态图（文档 05 图 5）完全一致。
2. **管理端接口缺少 URL 层角色拦截**：`SecurityConfig` 此前只有 `anyRequest().authenticated()`，
   角色校验仅存在于各 Service 的 `requireAdmin`，学生请求管理端接口会返回
   HTTP 200 + 业务错误码 403，且配置好的 `RestAccessDeniedHandler` 从未生效。
   已增加 `.requestMatchers("/api/v1/admin/**").hasRole("ADMIN")`，实现 URL 层 403 与业务层校验的双重防护。

## 十一、已知限制与后续建议

1. **论文全文解析**：当前索引语料来自题录与摘要，尚未接入 PDF/Word 正文抽取；建议第三阶段的后续迭代引入
   文档解析库并把解析结果写入 `literature_chunk`，阅读页无需改动即可展示。
2. **向量与混合检索**：混合检索（BM25 稀疏 + Milvus 向量稠密 + RRF 融合）已实现并通过实测（见第八节）。
   仍需注意：① 分块向量需先写入 Milvus（管理端 `POST /admin/rag/literature-vectors/rebuild`），
   未写入时检索自动退化为纯稀疏；② Milvus 维度必须与 embedding 模型一致（2560）；
   ③ 融合后仍接入了外部重排模型，如需对比纯 RRF 效果可关闭 `app.ai.retrieval.rerank-enabled`。
3. **测试覆盖**：目前包含上下文装配、AI 调用重试（`AiClientRetryTest`）、引用格式化（`CitationFormatterTest`）、
   BM25 稀疏检索（`SparseRetrieverTest`）与 RRF 融合（`RrfFusionTest`）共 18 个用例；
   建议继续补充主链路接口测试、权限测试与异常流程测试。
4. **命名遗留**：文件模块部分接口仍沿用模板期的 `tickets` 路径（如 `/api/v1/files/tickets/{ticketId}`），
   建议统一改名为文献资源语义，避免答辩时被追问。
5. **环境依赖**：RustFS 未启动时文献上传/下载会明确失败（错误码 `FILE_UPLOAD_FAILED` / `LITERATURE_FILE_MISSING`），
   其余功能不受影响；演示前请确认 MySQL、RustFS 与（可选的）Milvus 均已启动。
